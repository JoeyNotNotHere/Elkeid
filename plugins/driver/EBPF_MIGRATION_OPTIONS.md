# Driver 模块 eBPF 迁移方案对比分析

基于 Elkeid 现有的架构（Rust 用户态插件 + 自定义二进制协议 + 支持多版本灰度下发），针对 **方案 1（完全自研）** 和 **方案 2（基于开源二次开发）** 的详细对比分析如下。

## 方案 1：完全自研 (Build from Scratch)

**定义**：使用 `libbpf` (C) + `libbpf-rs`/`aya` (Rust) 技术栈，重新编写内核态 eBPF 代码和用户态加载/消费逻辑。

### 1. 可行性分析
*   **技术可行性**: **高**。Elkeid 团队对现有业务逻辑最熟悉，自研能确保 100% 贴合需求。
*   **架构融合**: **完美**。可以继续使用 Rust 开发用户态插件，代码风格、构建流程与现有项目完全一致。

### 2. 复杂度与成本
*   **开发复杂度**: **极高**。
    *   **内核态**: 需亲自编写 C 代码处理每一个 Hook 点，解决 Verifier 报错（循环、栈溢出），处理并发竞争。
    *   **兼容性**: 需自己解决 **CO-RE** 在不同内核上的适配，特别是针对 CentOS 7 等老旧内核，需手动维护 BTF 库或降级方案。
*   **维护成本**: **前期高，后期平稳**。
    *   前期需要投入大量精力修复 Kernel Panic（极少见但可能）、数据丢失、Verifier 拒绝等底层问题。
    *   后期代码库纯净，没有冗余功能，维护负担集中在核心逻辑上。

### 3. 优缺点
*   **优点**: 性能最优（无冗余），代码完全自主可控，无第三方依赖风险。
*   **缺点**: 开发周期长，对团队内核开发能力要求极高。

---

## 方案 2：基于开源项目二次开发 (Fork & Adapt)

**定义**：引入成熟的开源项目（如 **Tracee**），复用其内核态 Hook 代码和用户态加载逻辑。用户态插件改用 Go 语言重写（基于开源组件），并在用户态进行数据格式适配。

### 1. 可行性分析
*   **技术可行性**: **极高**。Elkeid 支持多版本下发，允许不同机器运行不同技术栈（Rust/Go）的插件。
*   **架构融合**: **中等**。引入 Go 语言栈，需要调整构建和发布流程，但在运行时是独立的进程，互不影响。

### 2. 复杂度与成本
*   **开发复杂度**: **中等**。
    *   **内核态**: **复用为主**。Tracee 等项目已实现了 `execve`, `connect` 等核心事件的 Hook，且经过了大规模验证。仅需补充 Elkeid 特有但开源项目缺失的少量 Hook（如特定的 Rootkit 检测）。
    *   **用户态**: **适配为主**。利用开源项目的 Go SDK 加载 eBPF，重点工作在于编写 `Adapter`：将开源项目的 Event 结构体转换为 Elkeid 的 Protobuf/二进制格式。
*   **维护成本**: **中等**。
    *   **上游同步**: 需关注开源项目的更新。如果只使用其核心库（如 `libbpfgo` 和基础 `bpf.c`），耦合度较低，升级相对容易。
    *   **问题排查**: 遇到底层问题时，可以借助开源社区的力量，或参考其 Issue 列表。

### 3. 优缺点
*   **优点**: **开发效率高**（避开了最难的 eBPF 加载/验证/兼容性适配），稳定性有社区背书，能快速产出可用版本。
*   **缺点**: 引入了 Go 技术栈，增加了包体积（Go 二进制通常较大），可能存在字段冗余（Over-fetching）导致轻微性能损耗。

---

## 综合对比与建议

| 维度 | 方案 1：完全自研 | 方案 2：基于开源二次开发 |
| :--- | :--- | :--- |
| **开发周期** | 长 (数月) | 短 (数周) |
| **技术栈** | Rust + C (保持一致) | Go + C (引入新栈) |
| **内核态工作量** | 100% (全部重写) | 20% (仅补充缺失事件) |
| **用户态工作量** | 100% (重写加载/通信) | 40% (复用加载，重写通信/适配) |
| **兼容性适配** | 需自建基础设施 | 复用开源社区成果 (CO-RE/BTFHub) |
| **性能/体积** | 最优 | 略差 (Go Runtime + 冗余字段) |
| **维护模式** | 查己方代码 | 查己方代码 + 关注上游 |

### 最终建议

**推荐选择：方案 2（基于开源二次开发）**。

**理由**:
1.  **避坑**: eBPF 的深水区在于**多内核版本的兼容性适配**（CO-RE, BTF, Verifier quirks）。开源项目（如 Tracee）在这方面已经踩过无数坑，直接复用其成果是极其明智的。
2.  **解耦**: Elkeid 的灰度下发机制完美支持了这种“异构插件”的模式。用户态用 Go 重写并不会影响 Agent 主进程。
3.  **聚焦**: 团队可以将精力集中在**业务数据适配**（如何把采集到的数据变成 Elkeid 需要的格式）上，而不是消耗在底层的内核调试上。

**实施路径**:
1.  以 **Tracee** 为蓝本。
2.  新建 `plugins/driver-ebpf` (Go 项目)。
3.  复用 Tracee 的 `libbpfgo` 加载逻辑和 `rules` 目录下的核心 `bpf` 代码。
4.  编写 Go 代码对接 Elkeid Agent 的通信管道，实现数据转换。
